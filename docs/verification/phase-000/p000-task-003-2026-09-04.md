# Phase 000 task 003 Pixelmon capability classification

## Scope and result

This packet records `P000-TASK-003` for the exact Pixelmon 9.4.0 capability review. It separates read and precheck behavior from mutation, receipt lookup, and retry. The result is deterministic and intentionally conservative. Exact Pixelmon account lookup and balance precheck are represented. Direct FutureShops withdrawal, deposit, receipt lookup, and retry are rejected before any provider mutation because the reviewed Pixelmon API has no durable request identity or outcome lookup.

The exact read only adapter remains optional and is loaded through runtime class names. Standard NeoForge startup remains independent of Pixelmon. This classification does not implement or authorize the native `PlayerPartyStorage` transaction mixin. That work belongs to Phase 002 after this capability boundary.

## Reviewed exact surface

The review used `/tmp/Pixelmon-1.21.1-9.4.0-universal.jar` with SHA 256 `9020393f98382ae8794ef2694e7bec1984c1a0eca735ea3eea06e0cb151c61f2` and SHA 512 `b1485031c27cbe0dd7125f11d3b003954e654f66c102479d443841071a37131067371bfc5e1fc2d8bf96a7195afa3ca02fc1525d343fc096d5bc598680bccafe`. `javap -public` and `javap -c -p` were run against the unchanged jar.

The exact declarations provide the following facts.

* `BankAccount` exposes UUID identity, `BigDecimal` balance, `hasBalance`, and boolean `add` and `take` operations.
* `BankAccountManager` and `BankAccountProxy` expose synchronous and asynchronous account lookup.
* `PlayerPartyStorage` implements `BankAccount` and stores the native balance in `pokeDollars`.
* `EconomyEvent.PreTransaction` and `EconomyEvent.SetBalance` are cancellable. `EconomyEvent.PostTransaction` reports old and new balances.
* `StorageProxy`, `StorageSaveAdapter`, and `StorageSaveScheduler` expose lookup and save interfaces but no request receipt contract.

The decompiled `PlayerPartyStorage` methods write `pokeDollars` to the `pixelDollars` NBT field. `setBalance`, `add`, and `take` update the field, call `updatePlayer`, and call `setNeedsSaving`; `add` and `take` then post `PostTransaction`. None accepts a FutureShops request UUID, durable receipt key, or retry token. The events contain transaction type and balance values only. Ordinary dirty marking is not an atomic receipt journal.

## Capability matrix

The public `EconomyCapability` order is `BALANCE_QUERY`, `PRECHECK`, `WITHDRAW`, `DEPOSIT`, `RECEIPT_LOOKUP`, and `IDEMPOTENT_RETRY`. `PixelmonEconomyProvider` declares exactly `true, true, false, false, false, false`.

| Operation | Exact Pixelmon surface | FutureShops classification | Failure behavior |
| --- | --- | --- | --- |
| balance query | `BankAccountProxy` lookup, `getIdentifier`, and `getBalance` | supported when account identity and exact integer conversion pass | typed unavailable result for absent account, mismatch, null, exception, fractional value, or overflow |
| debit precheck | `hasBalance(BigDecimal)` after exact conversion | supported for withdrawal, transfer debit, and fee requests | typed rejection for insufficient funds or typed unavailable result for provider failure |
| withdrawal | boolean `take(BigDecimal)` | unsupported for FutureShops mutations | `CAPABILITY_MISSING`, no `take` call |
| deposit | boolean `add(BigDecimal)` | unsupported for FutureShops mutations | `CAPABILITY_MISSING`, no `add` call |
| receipt lookup | no Pixelmon receipt API | unsupported | `CAPABILITY_MISSING`, no local receipt substituted |
| idempotent retry | no request identity or deduplication API | unsupported | `CAPABILITY_MISSING`, no retry attempted |

The adapter uses `RoundingMode.UNNECESSARY` and `longValueExact` for conversion. A nonintegral or out of range `BigDecimal` cannot become a silently rounded minor unit. Account identity must equal the requested player UUID. Reflection failures, absent implementation, null accounts, null balances, and mismatched identifiers become typed unavailable results. No exception is converted to a balance or success.

## Mutation and recovery safety

`withdraw`, `deposit`, and `retry` return the common mutation refusal. `lookup` returns a capability missing result explaining that Pixelmon does not expose durable economy receipts. The provider therefore cannot enter the coordinator's mutation path, which requires precheck, withdraw, deposit, receipt lookup, and idempotent retry together. The coordinator refusal occurs before journal append, custody creation, inventory movement, claim creation, analytics, events, or a Pixelmon `take` or `add` call.

The local FutureShops request UUID remains useful for the local journal, but it cannot make an external boolean method idempotent. A balance comparison after a crash cannot identify which caller changed the account. Native Pixelmon mutation remains unavailable until the Phase 002 mixin supplies a durable receipt beside the native account data, deduplicates the exact request UUID, and proves a durable save boundary.

## Conclusion and downstream contract

`EXT-003` is classified as query and precheck available, with direct mutation, durable receipt lookup, and idempotent retry unavailable. This is the required safe refusal result, not a general Pixelmon compatibility claim. The native exact `PlayerPartyStorage` mixin may add a separate request aware path only when both mods are present and only after Phase 002 proves its receipt, deduplication, account classification, save, restart, and recovery behavior. Hybrid or Vault accounts must not be treated as native Pixelmon accounts.
