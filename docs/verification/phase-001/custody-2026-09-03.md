# Phase 001 custody and claim checkpoint

Date: 2026-09-03

This checkpoint covers the durable custody and claim boundaries, the server shop buy and sell coordinator route, and the player shop buyback escrow route. It is not a phase completion record. The player shop crash matrix, external provider adapters, and the full restart matrix remain unfinished.

## Implemented behavior

* `EconomyCustodySavedData` persists bounded item identity, owner, quantity, content hash, state, schema version, checksum, and clean marker.
* `EconomyClaimSavedData` persists claimant, exact amount, bounded description, state, schema version, checksum, and clean marker.
* `PlayerShopBarterEscrowSavedData` persists exact serialized barter payment stacks, buyer and shop identity, state transitions, schema version, checksum, and clean marker. The player shop path writes `PREPARED` before removal, verifies the collected stack bytes, records `REMOVED` before storage insertion, records `STORED` after insertion, and records `COMPLETE` only after sale delivery.
* `PlayerShopSaleEscrowSavedData` persists exact serialized sale output stacks, buyer and shop identity, state transitions, schema version, checksum, and clean marker. The player shop buy path writes `PREPARED` before barter removal or economy debit, verifies the extracted stack bytes, records `REMOVED` before buyer delivery, and records `DELIVERED` and `CLAIMED` after delivery. Admin shop buys persist and mark freshly minted output removed before charging, then hold coordinator custody until delivery finalization. Failed pre delivery paths are `REFUNDED`; interrupted or unproven transitions are `RECOVERY_REQUIRED`.
* Player shop buyback persists the seller's exact item stacks in `PlayerShopBarterEscrowSavedData` before removal, verifies the removed bytes, records `STORED` before the owner's debit, and completes only after the owner debit and seller credit are confirmed. Admin shop buyback uses the same escrow and records the admin sink as `STORED` before the seller credit. Unsupported, unavailable, ambiguous, or unprovable legs refuse or retain the escrow in `RECOVERY_REQUIRED`; proven rollback restores the exact stacks when storage and inventory capacity permit it.
* Player shop settlement SavedData uses schema version 2 with a deterministic SHA 256 content checksum and clean shutdown marker. It reserves a stable claim request and amount before provider credit, preserves new sales while the claim is in flight, and subtracts only the confirmed claim amount.
* Settlement claims verify local claim delivery and resolution after provider confirmation. A claim finalization exception, unexpected claim state, or settlement persistence failure freezes the lifecycle and leaves the durable claim and settlement request available for recovery instead of reporting success.
* Invalid checksums, malformed entries, duplicate identities, and unknown newer schemas are read only blockers.
* The coordinator holds an entitlement before a provider leg, releases it on a proven rejection, and retains it for ambiguous recovery. Online buys advance through `DELIVERED` to `CLAIMED`. Sells retain `HELD` until stock settlement and then release.
* Server shop delivery never drops a paid reward after a confirmed debit. An insertion or custody claim failure freezes the lifecycle and leaves the durable entitlement unresolved. Server shop sells retain held custody through provider rejection and stock compensation until exact inventory restoration and custody release are proven.
* Physical money deposits restore coins only after a definitive provider rejection. Ambiguous deposits, failed compensation, and custody finalization remain recovery required. Withdraw builds and inserts all minted bill stacks atomically before registering mint records, so a partial payout cannot be silently forgotten.
* Pure barter captures the exact main inventory and offhand slots before ingredient removal. Partial removal, stock reservation rejection, and reward insertion rejection restore that snapshot and report a server error if restoration cannot be proven. Ingredient definitions reject non positive counts and use checked merging.
* Offline `/shopadmin view` balance reads use the typed coordinator result and refuse with the economy unavailable message during missing, draining, recovering, or frozen provider states instead of throwing from the legacy provider view.
* `BalanceManager` includes journal, custody, claims, barter escrow, and player shop settlement data in startup integrity and clean shutdown marker ordering. Settlement claims continue to recover through their shared journal request without treating ordinary pending proceeds as an incomplete economy mutation. After journal recovery, held item custody, incomplete economy claims, or non terminal barter escrow transitions the lifecycle to `FROZEN` with an operator recovery diagnostic instead of returning to `READY` while durable delivery state is unresolved. Shutdown attempts every index flush even when one throws, logs the affected index, always releases in memory handles, and leaves the clean marker unwritten unless the ordered drain gate succeeds.
* Startup now reconciles every incomplete journal request through the provider's durable outcome lookup before exposing the provider. A confirmed or definitive rejection can return the lifecycle to `READY`; an unknown outcome remains `FROZEN`.

## Security review

The scoped review covered the pure barter payment path and its rollback helper in `PlayerShopBlockService`, including the separate barter storage boundary, settlement persistence result, inventory restoration, and no drop overflow behavior. It also covered startup reconciliation of incomplete journal records through the provider lookup boundary. The recovery loop is bounded by the persisted journal snapshot, does not accept client input, and preserves the frozen state when lookup cannot prove an outcome. No new authorization, packet, path, deserialization, secret, or optional dependency exposure was found in these changes. The source scan regression tests and jar classpath scan pass, and the repository secret pattern scan found no matches.

GitHub reports one existing medium Dependabot alert on the default `1.20.1` branch for `org.apache.logging.log4j:log4j-api`. The 1.21.1 runtime resolves Log4j API `2.22.1` transitively through the pinned NeoForge toolchain. The alert is outside this focused change and remains a release review item.

The complete player shop crash and restart matrix still needs runtime injection at every escrow transition. An interrupted non terminal barter escrow is now durable and keeps the economy in recovery rather than being discarded or retried blindly. Exact external provider runtime proof remains an open phase gate.
