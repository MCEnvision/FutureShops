## Architecture and Implementation Boundaries

The logical server, provider API, coordinator, persistence, adapters, and client presentation remain owned by their earlier phases. Phase 003 changes implementation only to resolve a proven defect through the owning stable requirement. It never patches evidence, relaxes an assertion, substitutes a different external stack, or documents a failure as support.

Candidate identity is content based. Every runtime manifest records source commit, jar SHA 256 and SHA 512, Minecraft, NeoForge, Java, external artifact hashes, configuration, player count, expected result, actual result, and sanitized evidence location. No balance mirror, production player data, credential, private log, or mutable external state enters evidence.

### Issue 66 guidance contract

The post-artifact issue update translates validated behavior into architecture guidance without copying `2.3.0` implementation or prescribing source paths. Its read-back body must cover all of the following contracts.

1. **One economy gate.** Every buy, sell, cart, player shop, offline proceeds, pay, administration, analytics, future ATM, and other monetary mutation enters one server-owned gate. Callers never invoke the provider, internal balance store, journal, or custody service directly.
2. **Write-ahead state and identity.** Every root operation and money leg has a stable request identity. Intent is checksummed and durably flushed before an external effect. A matching local receipt audit record is durably written for each transition under `world/data/futureshops/receipts`. Outcome, custody, claim, and compensation transitions are durable and replay-aware. The receipt audit journal records FutureShops evidence only and does not prove that a Vault, Pixelmon, or DanConomy effect is safe to replay. A clean-shutdown marker is written only after journal, receipt audit records, custody, claims, and outcomes are flushed.
3. **Escrow and custody order.** A buy places the recoverable item in FutureShops custody before debit, then delivers it or creates a durable claim only after debit is proven. A sell moves the player's item into custody before credit, then finalizes the sale only after credit is proven. Failure before a proven external effect returns or preserves custody deterministically; failure after an ambiguous effect never guesses.
4. **Lifecycle admission.** `READY` admits capability-supported requests. `DRAINING` rejects new monetary work, lets admitted work reach durable boundaries, flushes all state, and only then permits a clean stop. `RECOVERING` runs before readiness after an unclean start and blocks new money work while requests are classified. `FROZEN` blocks monetary mutations whenever an outcome, originating provider, journal integrity, or recovery action cannot be proven.
5. **Capability negotiation.** Providers declare authoritative balance query, precheck, withdraw, deposit, durable receipt lookup, and idempotent retry separately. The gate verifies capabilities and enables each surface only when its entire required set passes. Missing, late, incompatible, or failing providers never trigger internal fallback.
6. **Pixelmon native-account contract.** Pixelmon `9.4.0` balance, precheck, boolean `add`, and boolean `take` calls do not prove a crash-window result. The Forge `1.20.1` implementation must inspect the exact `PlayerPartyStorage` and save classes, then target the native account with a request-aware mixin loaded only when FutureShops and Pixelmon are both present. It must persist the request UUID, operation, amount, and outcome receipt beside `pixelDollars`, deduplicate retries, force a durable save, and refuse custom or hybrid accounts. Unscoped Pixelmon calls retain native behavior and remain outside the FutureShops transaction contract. A local journal or observed balance delta is not a substitute.
7. **DanConomy exact ledger contract.** Exact DanConomy `1.2.1` on NeoForge `1.21.1` may register `danconomy` only when one unambiguous default currency uses `LEDGER` backing. Original FutureShops adapter and mixin code must bind the stable request UUID to the balance effect and immutable result receipt in the same `danconomy_ledger` saved-data image, return stored results for identical retries, reject conflicting reuse, and acknowledge only after proven synchronous durable replacement. Ordinary DanConomy calls retain native behavior. `PIXELMON_MIRRORED`, missing, ambiguous, incompatible, or unproven paths refuse before intent or custody. FutureShops must not copy DanConomy source or assets, alter or rebuild its jar, bundle its bytes, or redistribute it. DanConomy `1.2.1` does not itself supply a Forge `1.20.1` target, so that line adopts the provider and receipt architecture only unless an exact compatible artifact is separately proven; the future `1.21.1` port revalidates the exact adapter and targets.
8. **Bridge contract.** A separate bridge may register `vault` through the public provider API and owns Bukkit, Vault, hybrid runtime, and economy-plugin dependencies. Phase 002 must produce a disposable bridge or backend proof, or an exact implementation trace, that persists the balance effect and provider receipt in one transaction, demonstrates interruption before and after commit, looks up the original request, and deduplicates retries. The current PixelmonEconomyBridge and FinalEconomy path requires modification before mutation can be enabled. FutureShops core must not link, reflect into, bundle, or fall back through Bukkit or Vault.
9. **Backups and restoration.** Backups include a mutually consistent FutureShops journal, the receipt audit directory at `world/data/futureshops/receipts`, outcomes, custody index, claims, clean marker, configuration, selected and originating provider identities, artifact manifest, and checksums. Native Pixelmon and DanConomy provider receipt data and every other external provider's data remain authoritative and are backed up under that provider's procedure. FutureShops never restores, mirrors, or fabricates an external balance from its own backup or local receipt audit record.
10. **Operator reconciliation.** An unresolved request or unknown receipt record remains frozen or recovering as required and exposes request ID, provider ID, amount and direction, custody state, last durable transition, and sanitized diagnostic context. Automated retry or compensation is allowed only from a durable provider receipt or idempotent provider result, never from the local receipt audit directory alone. Otherwise the operator preserves all data, restores the exact provider stack, performs documented evidence-based reconciliation, and records the resolution without direct balance guessing.
11. **Required `3.0.0` work.** The Forge `1.20.1` beta must route its existing escrow, market, shops, commands, offline proceeds, claims, and future ATM boundaries through this contract, add schema versioning and migration for journal, lifecycle, custody, and recovery state, provide capability and crash tests, and preserve existing saves. It may reuse the DanConomy adapter architecture but cannot claim DanConomy `1.2.1` compatibility on Forge `1.20.1`. The future `1.21.1` port must revalidate loader lifecycle, saved-data behavior, networking and client synchronization, exact Pixelmon, DanConomy, and hybrid artifacts, mixin targets, adapter isolation, Java and dependency versions, and the full runtime and recovery matrix rather than assuming the Forge proof transfers.

The issue must distinguish required behavior from suggested component names, preserve `FUT-001` and `FUT-002` as future work, and state that issue text and the validated `2.3.0` artifact are design evidence only. They do not prove either `3.0.0` line is implemented, migrated, compatible, or released.
