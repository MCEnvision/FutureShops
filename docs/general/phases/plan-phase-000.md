## Purpose and Ownership

This phase establishes the only platform and public provider contract on which later economy routing may depend. It reconfirms the repository and toolchain baseline, resolves every external prerequisite from `EXT-001` through `EXT-006`, proves that Pixelmon and the separate Vault bridge model can meet exact value and idempotency guarantees, updates the product and NeoForge pins, freezes the public provider API, and implements restart only provider selection without routing gameplay surfaces through external providers yet.

This phase owns `CORE-REQ-001`, `CORE-REQ-002`, and `CORE-REQ-003`. The master owns product scope, locked decisions, phase order, external prerequisite definitions, and release boundaries. This file owns only the dependency ordered execution, verification, failure handling, and evidence packet for `CORE-PHASE-000`. It does not authorize weakening a master requirement when external evidence is unavailable.

## Scope Boundaries

### Included Scope

- `CORE-REQ-001`: Reconfirm the full baseline, set FutureShops to `2.3.0`, pin NeoForge exactly `21.1.248`, preserve Minecraft `1.21.1` and all unrelated pinned boundaries, and prove one jar remains suitable for client and dedicated server.
- `CORE-REQ-002`: Freeze and implement a public NeoForge provider API with deterministic registration, stable identifiers, API compatibility version `1`, validated currency metadata, typed lifecycle readiness, authoritative queries, exact checked integer minor units, durable request identity, typed idempotent outcomes, durable outcome lookup, threading rules, and provider failure containment.
- `CORE-REQ-003`: Add one validated server controlled provider selection, default it to `internal`, resolve it once per server lifecycle, freeze the active selection before monetary readiness, and stage selection changes for restart without fallback or hot activation.
- `EXT-001`: Acquire and review exact official Pixelmon `9.4.0` runtime and development artifacts, including provenance, terms, hashes, archive and dependency inspection, security findings, and redistribution conclusion.
- `EXT-002`: Provision and record a disposable Pixelmon environment using Minecraft `1.21.1`, NeoForge `21.1.248`, the exact reviewed Pixelmon artifacts, and the exact tested FutureShops build.
- `EXT-003`: Prove Pixelmon economy API feasibility for exact minor units, lifecycle, persistence, durable identity, duplicate prevention, and deterministic recovery.
- `EXT-004`: Acquire and review the exact separately installed bridge artifact that registers `vault`, without adding its code or dependencies to FutureShops.
- `EXT-005`: Select and review one exact hybrid runtime, Vault, and economy plugin artifact set, including provenance, hashes, terms, archive and dependency inspection, compatibility, and security conclusions.
- `EXT-006`: Provision and record a disposable hybrid environment using only the exact reviewed stack, separate bridge, and exact tested FutureShops build.
- Phase owned documentation for the public API, provider selection, platform change, artifact provenance, feasibility conclusions, environment reproduction, and explicit blocker handling.

### Explicit Exclusions

- `CORE-REQ-004` through `CORE-REQ-016`: Complete provider routing, transaction coordination, market surface migration, player presentation, recovery implementation, and operational behavior belong to `CORE-PHASE-001`. Phase 000 freezes their required public contracts but does not start their implementation.
- `CORE-REQ-017` and `CORE-REQ-018`: Production implementation and full compatibility validation of the Pixelmon adapter and separate Vault bridge belong to `CORE-PHASE-002`. Phase 000 proves feasibility and provides reproducible reviewed inputs only.
- `CORE-REQ-019` through `CORE-REQ-021` and the Phase 003 portion of `CORE-REQ-022`: Plan wide production validation, terminal documentation reconciliation, final artifact creation, and verification and update of the already open GitHub continuation issue belong to `CORE-PHASE-003`.
- Initial issue creation and `EXT-007` authoring evidence are completed immediately after plan validation, before this phase begins. This phase does not modify or close the issue; Phase 003 revalidates `EXT-007` and updates the same issue after product validation.
- `FUT-001` through `FUT-004`: `3.0.0` maintenance, the future `1.21.1` port of `3.0.0`, an ATM interface or command, and additional provider adapters remain future work.
- `NG-001` through `NG-009`: Publication, balance migration, bundled Bukkit or Vault components, hot switching, shadow balance ledgers, extra Pixelmon versions, unrelated upgrades, telemetry, distributed authority, and weakened browsing, barter, custody, claims, or save compatibility remain prohibited.

- No external artifact may be committed, redistributed, or used as evidence until its applicable terms and provenance have passed review.

## Architecture and Implementation Boundaries

The dependency direction remains client presentation to server entry points to economy orchestration to the public provider API and frozen registry. Phase 000 establishes the lowest public boundary and selection snapshot. It must not route shops, carts, player shops, markets, commands, packets, analytics, claims, or physical money behavior ahead of `CORE-PHASE-001`.

Provider registration uses one verified NeoForge `1.21.1` lifecycle window. The exact event and bus are selected from repository and official lifecycle evidence, not assumed from another loader or Minecraft version. Registration is server independent where registration semantics require it, but provider factories or services must not capture a world, player, or logical server before the server context exists. Registry freeze occurs deterministically before monetary readiness. Duplicate identifiers, reserved identifier misuse, invalid metadata, incompatible compatibility versions, registrations after freeze, or ambiguous factories yield a typed rejected registration and cannot win by mod load order.

The provider identifier is a stable lowercase resource identifier validated before insertion. `internal` is owned by the built in provider. `vault` is reserved for the separately installed bridge. The bundled Pixelmon identifier must be written into the allocation record during this phase after its exact integration evidence is known; it cannot remain implicit or be inferred from display text. Identifier comparison is locale independent. Compatibility version `1` is independent from FutureShops `2.3.0`; exact supported compatibility versions are checked before provider construction or readiness.

Currency metadata is immutable after selection and includes validated singular and plural display names and minor unit precision. Empty, control character bearing, excessively large, contradictory, negative precision, or unsupported precision metadata rejects the provider as incompatible. Display metadata never authorizes money movement. Any localization boundary is explicit, and no provider supplied string becomes an unsafe translation key or formatting template.

The API uses one fixed signed integer minor unit representation selected and documented during implementation from repository and Pixelmon evidence. All public conversion, addition, subtraction, multiplication, aggregation, and bounds operations are exact and checked. Domain rules reject negative or zero values where prohibited. External decimals, binary floating point, nonfinite values, fractional minor units, excessive precision, overflow, underflow, and locale dependent parsing fail before provider or custody mutation. A balance query may carry a negative value only if the frozen provider contract explicitly permits it; transaction amounts remain domain validated independently.

Readiness and outcomes are typed contracts. A query either returns a validated authoritative value or a typed nonvalue state. It never maps unavailable, invalid, thrown, or ambiguous provider behavior to zero. A mutation result distinguishes confirmed effect, definite no effect rejection with reason, duplicate completion returning the original outcome, and unknown or ambiguous effect requiring recovery. Stable reason categories include unavailable, incompatible, invalid amount, insufficient funds, permission denied, duplicate completion, provider failure, and recovery required. Provider exceptions are caught at the boundary and classified without losing safe diagnostic context.

Every mutation request accepts a stable server owned request UUID and enough immutable operation context for the provider to distinguish a logical operation. Multi leg child identity and the durable transaction schema are implemented in `CORE-PHASE-001`, but the public API contract must already support deterministic child calls, original outcome lookup, and idempotent retry. A provider that exposes only an unauditable change balance call does not satisfy the contract. An adapter owned receipt strategy must close the crash window between external effect and local durable outcome. Comparing before and after balances is not sufficient when concurrent changes are possible.

Registration executes in its verified lifecycle context. Provider readiness, authoritative queries, mutations, and recovery calls execute only on the logical server execution model unless the frozen contract explicitly marshals a result back before state change. Providers must not perform blocking filesystem or network I/O, registry discovery, full balance scans, or retry loops in gameplay paths. The phase fixture asserts the required thread. Runtime failure transitions are implemented in the next phase, but the phase 000 API must express them without breaking or changing signatures.

Provider selection is server controlled. An absent key means `internal`. An explicit malformed, unknown, incompatible, missing, or late external selection preserves the requested identifier for safe diagnosis, keeps the server online, and does not select `internal`. The active identifier and its validated metadata resolve once per server lifecycle. A config reload may validate and stage a next identifier, preserve other last valid settings according to the repository config system, and report restart required, but cannot replace the active provider. No selection change migrates balances, prices, physical bills, or unresolved request ownership.

Phase 000 must document its schema impact. The provider compatibility number, identifier allocation, metadata shape, result categories, configuration key and default, and any serialized configuration representation are versioned contracts. Existing world balance data must not be rewritten merely because the selection feature is installed. If implementation introduces persistent records despite phase scope, their schema, migration, unknown version behavior, backup and rollback impact must be reviewed explicitly; otherwise the preferred outcome is no new world persistence until the transaction coordinator phase.

Optional integration linkage is isolated. The public API and standard startup cannot load Pixelmon classes when Pixelmon is absent. FutureShops cannot reference Bukkit, Vault, a hybrid runtime, the bridge, or an economy plugin directly or reflectively. External artifact files stay outside tracked source and final jar. The same FutureShops candidate bytes are installed on client and server, with server authority and dedicated server client class isolation preserved.
