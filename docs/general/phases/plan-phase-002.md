## Purpose and Ownership

This phase delivers and proves the two external integration outcomes authorized for FutureShops `2.3.0`: a bundled optional adapter for exactly Pixelmon `9.4.0` on Minecraft `1.21.1` and NeoForge `21.1.248`, and interoperability with the exact reviewed, separately installed bridge that registers provider identifier `vault`. The phase exists to turn the artifact and API feasibility evidence from `EXT-001` through `EXT-006` into implementation and real environment proof without weakening the provider, transaction, recovery, security, or packaging contracts integrated by `CORE-PHASE-001`.

The canonical requirements owned here are `CORE-REQ-017` and `CORE-REQ-018`. The master owns product scope, locked versions, provider behavior, phase topology, non goals, and the final unpublished endpoint. This file owns only the dependency ordered implementation, exact stack validation, failure handling, evidence, and handoff for these two integrations. It does not redefine the public provider API, genericize hybrid compatibility, authorize another Pixelmon version, or replace external artifact inspection with assumed API paths.

## Architecture and Implementation Boundaries

The dependency direction remains client presentation to server surfaces to economy orchestration and durable transaction coordination to the frozen public provider API. The bundled Pixelmon adapter implements that API and may depend only on the exact verified Pixelmon interfaces plus existing FutureShops public integration boundaries. No Pixelmon type may appear in common startup signatures, provider registry interfaces, public FutureShops API types, server paths loaded without Pixelmon, or client paths loaded on a dedicated server. Presence and exact version checks must occur before any optional class is linked. Registration occurs only during the frozen NeoForge lifecycle window and never by repeated gameplay discovery.

The separate bridge is outside the FutureShops artifact and implementation. It registers `vault` through the same public API available to any provider. FutureShops must not import, reflect on, discover, invoke, or package Bukkit, Vault, hybrid runtime, economy plugin, or bridge types. The exact hybrid stack may be inspected and exercised as a fallible external system, but no result authorizes a generic hybrid or Vault claim.

For both providers, the logical server owns selection, readiness, player identity, permissions, request identities, transaction state, custody, claims, and outcomes. Clients receive presentation snapshots only. A stale client may send a navigation or action request, but the server revalidates provider state and either chooses an allowed nonmutating route or returns a typed rejection before provider or custody mutation.

Currency metadata is validated and frozen at startup selection. The adapter or bridge supplies singular and plural display names and precision through the public API. The conversion algorithm must be derived from inspected artifact behavior. It may accept a value only when conversion to signed integer minor units and back is mathematically exact, within checked bounds, and stable across locale and serialization. No floating point value becomes authoritative, no rounding or exchange rate is applied, and no invalid provider response is treated as zero. Existing configured integer prices keep their magnitude and become minor units under the selected provider, so operator documentation requires a price review before selection.

Every mutation enters the integrated coordinator with a server owned root UUID and stable child identities. Intent is durable before the first external effect. Confirmed outcomes, provider identity, receipts, recovery state, and compensation relationships are persisted without mirroring balances. The Pixelmon adapter uses only the exact durable strategy proven by `EXT-003`; the bridge must demonstrate equivalent semantics through the public API. A timeout, exception, process interruption, missing acknowledgement, or service loss after an external effect is ambiguous until durable outcome lookup proves a result. Ambiguity enters `RECOVERY_REQUIRED`, blocks ordinary monetary writes, and permits only safe query, recovery, or compensation behavior.

All provider calls are bounded and occur on the server execution model declared by the public API. Optional discovery is startup only. Gameplay paths perform no filesystem access, dependency scanning, network discovery, full balance scans, shadow synchronization, or unbounded retry. Exceptions are contained at the provider boundary and logged once per transition or request category with provider identifier, safe request identity, lifecycle state, and action, without credentials or unnecessary private balances.

The complete surface contract applies identically to Pixelmon and `vault`: public queries and mutation APIs, administrative query and mutation, analytics, server shops, carts, player shops, offline proceeds, claims, pay, fees, refunds, events, rollback, reload, startup, and shutdown route through provider and coordinator boundaries. Deposit, withdrawal, money item activation and redemption, and any future ATM mutation remain disabled whenever an external provider is selected. Bills and their data remain registered and retained. Browsing and pure barter never invoke the provider and remain usable in unavailable and recovery states.

Persistent integration records use the upstream versioned schema and bind to the originating provider identifier. Unknown or newer records are preserved or rejected safely, never discarded. Restart with another selected provider cannot replay an unresolved request against that provider. Recovery restores the originating exact stack where possible, queries by stable identity, and compensates only after the original outcome is proven. External balances remain authoritative only in the external provider and are never copied into `BalanceManager` or analytics.
