## Purpose and Ownership

This phase implements and proves the two external integration outcomes authorized for FutureShops `2.3.0` on Minecraft `1.21.1` and NeoForge `21.1.248`. First, the same FutureShops jar contains an optional capability adapter for exactly Pixelmon `9.4.0`. When both mods are present, the phase inspects the exact Pixelmon classes and save path, then implements a narrow mixin for native `PlayerPartyStorage` accounts. The unmodified direct Pixelmon API remains query and precheck capable but mutation-refusing for FutureShops calls. The mixin adds a request-aware native entrypoint carrying the FutureShops request UUID, stores the provider receipt beside `pixelDollars`, deduplicates retries, and forces a proven durable save. It must refuse custom accounts and hybrid accounts returned by `BankAccountProxy`, while unscoped Pixelmon calls retain their native behavior. Second, a separately installed and reviewed bridge may register provider identifier `vault` through the public FutureShops API. This phase includes a disposable transaction proof for the bridge or economy backend, covering one-transaction balance and receipt persistence, interrupted commit, lookup, and retry. Only an exact bridge and backend whose declared mutation capabilities and crash-recovery behavior are proven may enable mutation-required surfaces. The currently observed PixelmonEconomyBridge and FinalEconomy path remains refused without that modification. DEC-019 authorizes obtaining or building a separate test registrant and durable backend inside this phase; their completed artifacts are outputs, not entry prerequisites. All integration workflows also emit DEC-021 correlated server diagnostics first, with a client run only when a client-only acceptance criterion remains after headless tests.

The canonical requirements owned here are `CORE-REQ-017` and `CORE-REQ-018`. The master owns product scope, locked decisions, global phase topology, compatibility claims, and the unpublished completion endpoint. This blueprint owns the dependency-ordered implementation, exact runtime proof, optional dependency isolation, failure and recovery behavior, packaging evidence, and downstream handoff for the two integrations. It does not reinterpret a boolean Pixelmon `add` or `take` result as a durable receipt, add an unsafe override, embed a mirrored balance ledger, bundle external artifacts, or claim generic Pixelmon, Vault, Bukkit, economy plugin, or hybrid-server compatibility.
