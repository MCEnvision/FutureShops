## Purpose and Ownership

This phase implements and proves the two external integration outcomes authorized for FutureShops `2.3.0` on Minecraft `1.21.1` and NeoForge `21.1.248`. First, the same FutureShops jar contains an optional capability adapter for exactly Pixelmon `9.4.0`. When both mods are present, the phase inspects the exact Pixelmon classes and save path, then implements a narrow mixin for native `PlayerPartyStorage` accounts. The unmodified direct Pixelmon API remains query and precheck capable but mutation-refusing for FutureShops calls. The mixin adds a request-aware native entrypoint carrying the FutureShops request UUID, stores the provider receipt beside `pixelDollars`, deduplicates retries, and forces a proven durable save. It must refuse custom accounts and hybrid accounts returned by `BankAccountProxy`, while unscoped Pixelmon calls retain their native behavior. Second, a separately installed and reviewed bridge may register provider identifier `vault` through the public FutureShops API. This phase includes a disposable transaction proof for the bridge or economy backend, covering one-transaction balance and receipt persistence, interrupted commit, lookup, and retry. Only an exact bridge and backend whose declared mutation capabilities and crash-recovery behavior are proven may enable mutation-required surfaces. The currently observed PixelmonEconomyBridge and FinalEconomy path remains refused without that modification.

The canonical requirements owned here are `CORE-REQ-017` and `CORE-REQ-018`. The master owns product scope, locked decisions, global phase topology, compatibility claims, and the unpublished completion endpoint. This blueprint owns the dependency-ordered implementation, exact runtime proof, optional dependency isolation, failure and recovery behavior, packaging evidence, and downstream handoff for the two integrations. It does not reinterpret a boolean Pixelmon `add` or `take` result as a durable receipt, add an unsafe override, embed a mirrored balance ledger, bundle external artifacts, or claim generic Pixelmon, Vault, Bukkit, economy plugin, or hybrid-server compatibility.

## Architecture and Implementation Boundaries

The server-owned economy gate remains the only entry point for balance-sensitive workflows. Provider capability metadata is frozen at restart-time selection and is not inferred from method presence alone. A surface declares the capabilities it requires. If any capability is absent, the gate returns a typed unavailable or unsupported result before preparing a write-ahead record or moving an item into custody. This early-refusal invariant remains mandatory for the unmodified direct Pixelmon `9.4.0` API, custom accounts, hybrid accounts, and any native mixin instance without a proven durable save.

The Pixelmon adapter may refer to reviewed optional types only behind the repository's established optional integration boundary. Ordinary common initialization, dedicated-server startup without Pixelmon, and client startup must not resolve Pixelmon classes. The adapter checks the exact mod identifier and version and exposes only exact, lossless query values. Phase 002 records the exact `PlayerPartyStorage` inheritance, `pokeDollars` field, `pixelDollars` NBT read and write, `add` and `take` behavior, and `StorageProxy` save adapter and scheduler path before editing the mixin. Boolean `add` and `take`, balance events, and prechecks are not receipts and do not authorize unscoped FutureShops mutation. When both mods are present, a narrow mixin adds a request-aware entrypoint only to exact native `PlayerPartyStorage` accounts. It persists the request UUID, operation, amount, before and after values, and outcome receipt beside `pixelDollars`, deduplicates a repeated UUID to the original outcome, and forces a proven durable save or atomic replacement before returning success. It must identify and reject custom implementations and the hybrid account returned through `BankAccountProxy`, while leaving unscoped Pixelmon calls at their native behavior. It does not make arbitrary Pixelmon or plugin calls transactional. The adapter stores no external balance and provides no compensation path that invents or rewrites Pixelmon money.

FutureShops does not implement a Vault adapter. The separately installed bridge registers `vault` through the same public NeoForge provider contract used by any external registrant. FutureShops contains no Bukkit or Vault imports, dependencies, reflection, service lookup, plugin lifecycle code, or bridge special case. Phase 002 owns a disposable bridge or backend proof harness, or an exact backend trace, that demonstrates one transaction for the balance effect and provider receipt, interruption before and after commit, request lookup, and retry deduplication. The bridge and economy backend own translation to the exact hybrid runtime and must persist the balance effect and provider receipt in one transaction. The currently observed PixelmonEconomyBridge and FinalEconomy path does not satisfy that contract without modification. FutureShops writes local request and transition evidence to `world/data/futureshops/receipts`, but the directory is an audit trail and cannot establish that a Vault operation completed or is safe to replay. FutureShops accepts `vault` mutation capabilities only after the phase proof and exact runtime proof demonstrate stable request identity, durable provider receipt lookup, idempotent retry, exact value conversion, one-transaction persistence, and typed failure behavior.

For an enabled `vault` mutation, the Phase 001 state machine remains authoritative: persist intent, the local receipt audit transition, and custody before the external effect, use stable root and leg identities, persist a proven provider outcome before delivery, and turn failed delivery into a durable claim. `DRAINING` rejects new work and lets bounded in-flight work settle before a clean marker that is written after the journal, receipt audit directory, custody, and claims are flushed. An unclean start or unknown receipt record enters `RECOVERING`; receipt lookup by stable identity decides a proven outcome. Missing or contradictory evidence enters `FROZEN`; no blind retry, fabricated refund, automatic external balance restore, or internal fallback is permitted.

All provider work executes on the required logical-server thread. Inputs, amounts, precision, player identity, permissions, provider identity, request identity, returned values, and collection or string bounds are validated. Checked integer minor-unit arithmetic is mandatory. External exceptions are contained and mapped to typed provider failure. Logs identify provider, request, operation, and recovery category without balances not needed for diagnosis, private player data, credentials, or secret-bearing configuration.
