## Purpose and Ownership

This phase delivers issue 33 as one bounded administrator workflow on Forge 1.20.1. An authorized administrator uses the existing searchable item grid, selects multiple identities from the server-approved registry snapshot, optionally binds one full exact canonical NBT compound to each selected item, enters one shared decimal price and stock value, reviews every generated listing and conflict action, and submits one atomic catalog mutation. Existing listings are skipped and reported by default. A replacement is possible only after an explicit choice for that one conflicting item, changes only bulk-owned fields, and preserves all unrelated and compatible unknown fields.

This file owns the execution blueprint for `CORE-REQ-007` and `CORE-REQ-008`. The master plan owns the product boundary, requirement meaning, phase order, final completion endpoint, branch versions, and exclusions. This phase must not create a second item selector, a fuzzy search language, an NBT path or predicate language, a global replace option, or a separate catalog schema. It extends the implemented editor and normalized catalog contracts from SRC-003 rather than reopening completed 3.1 editor work.

## Architecture and Implementation Boundaries

### Authority and data flow

1. The client opens the existing administrator grid from the current Server Shop editor route. The server supplies or confirms the finite registry identity set, snapshot fingerprint or equivalent revision, current catalog expectation, permission state, currency precision, stock limits, and maximum batch size.
2. The client searches only that snapshot and maintains a local draft. Each selected row contains one registry identifier and either no NBT or one complete exact NBT compound. Search text is presentation only and never enters identity matching.
3. Preview sends a bounded correlated proposal. The server rechecks permission and runtime readiness, resolves each registry ID, parses and canonicalizes each exact compound, validates numbers and template context, reads the current catalog, computes deterministic conflicts and generated listings, and returns every row plus an immutable preview fingerprint and expected catalog state.
4. The client renders every returned row. Default conflict state is skip. The administrator may mark Replace only on a unique eligible conflict. Any draft edit discards the preview token and disables commit until another preview succeeds.
5. Commit carries the stable request UUID, preview fingerprint, expected registry and catalog state, and explicit per-row actions. The server does not trust client display names, minor-unit conversion, listing IDs, conflicts, replacement targets, permissions, or completion state. It recomputes the candidate and requires exact agreement.
6. The catalog service applies the deep candidate once, publishes the validated snapshot, records the correlated outcome, and then refreshes active sessions. The result reports all rows and the resulting catalog expectation. The client closes only on its matching success response.

### Identity, ordering, and conflict rules

- Registry-only identity is the exact normalized resource location with absent NBT. Exact identity is that resource location plus one complete parsed compound in deterministic canonical form. Empty compounds normalize according to one documented rule and cannot compare both as absent and exact in different code paths.
- Canonical equality is structural, not source-string order. Semantically equal compounds produce one identity and one digest; distinct types, values, lists, or compounds remain distinct. Bounds cover raw encoded bytes, decoded depth, collection sizes, and packet size using the repository's existing safe limits or stricter tested phase-local limits.
- Rows are sorted by normalized registry identifier, then registry-only before exact identity, then canonical NBT digest with a deterministic collision-safe structural tie check. UI click order cannot change preview or write order.
- Duplicate selections collapse only when their canonical identities are equal and are reported to the administrator. A selected identity that matches one existing bulk-compatible listing is a conflict. Multiple possible existing targets or a target whose owned paths cannot be identified unambiguously is blocking and cannot be replaced through this workflow.
- Generated listing identifiers are deterministic against the complete candidate and do not depend on map iteration, locale, screen order, or a prior failed attempt. Explicit replacement retains the existing stable listing identifier unless the current schema contract requires an identity-owned value inside the listing body.

### Field ownership and preservation

The operation owns only the selected simple listing's item identity in the role established by the existing entry context, that component's exact-NBT state, the one shared price represented in that template, and the stock value. It may update derived revision or integrity fields required by the existing schema. It does not own display descriptions, categories, permission nodes, active state, expiry, schedules, limits, bundle comparisons, unrelated options or components, promotions, receipts, root metadata, or compatible unknown JSON members.

Replacement must merge into the raw target object using an explicit schema-path ownership table for the selected existing template. It must not normalize and rewrite an unrelated listing merely because the in-memory record cannot represent an unknown field. If a target is complex, ambiguous, forward-versioned, or not representable by the ownership table, preview marks it blocking or skip-only and directs the administrator to the existing editor. The complete merged root is parsed and validated before persistence.

### Network, compatibility, and security boundaries

- Every message has fixed direction, collection count, string, NBT, action, and total-byte bounds. Decode rejects malformed or oversized data before service dispatch. Handler execution occurs on the logical server thread.
- Preview and commit recheck permission level or the repository's current equivalent. Permission loss between them returns denied and changes no state. Player identity comes only from the network context.
- The protocol version advances from the exact merged Phase 002 value when packets change. Registration order, constant tests, wire tests, and handshake behavior update together. No compatibility shim may interpret the old packet as the new batch contract.
- Request UUID plus canonical payload fingerprint provides idempotency. An identical replay returns the prior complete result without another write. Same UUID with another fingerprint is a conflict. Disconnect does not imply success or retry permission until the server result or durable recovery state is resolved.
- Logs use bounded actor, request, catalog, row count, status, and safe registry identifiers. They must not emit private raw NBT, entire catalogs, credentials, or unbounded packet content.

### Persistence, concurrency, and performance

- Planning operates on immutable snapshots and performs no file write or live catalog mutation. Commit serializes against other administrator catalog mutations and verifies expected catalog state after acquiring the mutation boundary.
- Build and validate the complete candidate in memory. Prepare every reload-dependent representation before the authoritative file replacement where current APIs permit. The success path performs one logical catalog write and one in-memory publication.
- Failure before replacement leaves disk and memory untouched. Failure after replacement restores one complete matching backup and keeps or restores the old in-memory snapshot before reporting failure. If verified restoration cannot be proven, fail the service closed, preserve evidence, and do not advertise a mixed state as success.
- Session refresh happens after commit and cannot alter catalog truth. A refresh delivery failure retains the committed result and causes clients to request the authoritative snapshot again; it must not repeat the catalog write.
- Registry enumeration, canonicalization, conflict scans, and JSON work occur only on open, preview, or commit, never each render frame or tick. Batch and catalog bounds prevent quadratic or unbounded work. Index existing identities once per plan.
